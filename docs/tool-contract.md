# Контракт Tool
## Общие границы

Tool — локальный шаг обработки, который получает типизированный вход и контекст попытки, возвращает типизированный результат или одну типизированную ошибку. Он не принимает HTTP-запрос, не пишет в JobStore, не меняет состояние Job и не планирует повторы. Registry хранит имя, версию, входную/выходную схему и ссылку на реализацию; Dispatcher выбирает и вызывает Tool.

Публичная операция `analyze_match` — цепочка `fetch_match_metadata@1 → build_match_report@1`. Оба Tool используются для каждого успешного Job. Произвольный запуск внутренних имён через API запрещён: `operation=fetch_match_metadata` даёт `400 UNKNOWN_TOOL` до создания Job.

| Часть контракта | Что передаётся / возвращается |
|---|---|
| Дескриптор | `name`, положительная целая `version`, имена схем входа/выхода, допустимые коды ошибок, предельное время. |
| Контекст | `job_id` UUIDv4, `attempt` 1–3, фиксированные версии Tool, UTC `deadline_at`, проверка оставшегося времени. Контекст внутренний; секрет клиента и ключ отправки Tool не получает. |
| Вход | Неизменяемое значение схемы конкретного Tool. Изменение полученного объекта запрещено. |
| Успех | Один выход конкретной схемы, включая предупреждения. Предупреждение не заменяет обязательные данные. |
| Отказ | Один объект Error: `code`, `message`, `retryable`, `retry_at`, `details`; форма совпадает с `components.schemas.Error` в [OpenAPI](api/openapi.yaml). |
| Побочные эффекты | Только чтение источника у первого Tool. Второй Tool использует локальный снимок справочника; записи Job/результатов делает Dispatcher. |

Возвратить одновременно успех и ошибку нельзя. Необработанное исключение Dispatcher преобразует в `INTERNAL_TOOL_ERROR` без stack trace в публичном ответе. Невалидный выход Tool превращается в `TOOL_OUTPUT_INVALID`; ничего не публикуется. Оба отказа неповторяемые автоматически.

<a id="validation"></a>
## Кто проверяет параметры

| Проверка | Ответственный | Результат отказа |
|---|---|---|
| HTTP, размер, JSON, секрет, ключ, обязательные поля | HTTP-вход | HTTP 400/401/413/415, Job отсутствует. |
| Операция и схема пользовательских параметров, нормализация uint64 | Dispatcher по Registry | HTTP 400, Job отсутствует. |
| Совпадение фактического внутреннего входа со схемой Tool | Dispatcher перед вызовом; Tool повторно защищает свои предусловия | `TOOL_INPUT_INVALID`; принятый Job становится `failed`, это дефект связки компонентов, не новое обвинение пользователя. |
| Типы и семантика ответа внешнего API, совпадение ID | `fetch_match_metadata` | `SOURCE_DATA_INVALID`; Job `failed`. |
| Проверка каждого дополнительного блока, построение отчёта | `build_match_report` | Предупреждение для блока; отказ только при нарушении обязательной части/лимитов обязательного результата. |
| Схема выхода Tool и межполевые инварианты | Сам Tool, затем Dispatcher на выходной границе | `TOOL_OUTPUT_INVALID`; публикации нет. |
| Переход состояния, token, lease, атомарность commit | Store по команде Dispatcher | Внутренний `INVALID_JOB_TRANSITION` / `STALE_ATTEMPT`; чужая/устаревшая запись отклоняется. |

`retryable` у Tool сообщает, допускает ли причина повтор. Решение зависит также от общего бюджета, `Retry-After` и состояния Job; повтор планирует только Dispatcher. Не более одного GET metadata на попытку, скрытые повторы в адаптере запрещены.

<a id="fetch"></a>
## Tool 1 — fetch_match_metadata@1

**Назначение:** получить один проверенный снимок metadata заданного матча, не инициируя Steam fallback.

**Вход `FetchMatchInput`:** объект ровно с `match_id` — нормализованной десятичной строкой в диапазоне 1–18446744073709551615. Контекст попытки передаётся отдельно. URL, ключ источника, таймаут, `disable_steam` и число повторов пользователь не задаёт.

**Зависимость:** DeadlockApiAdapter. Он делает ровно один `GET https://api.deadlock-api.com/v1/matches/{match_id}/metadata?disable_steam=true`, не следует редиректам, ограничивает весь запрос 30 секундами и 32 MiB после распаковки. Глубина JSON — до 64. Внешний API-ключ, если оператор его настроит, находится только внутри адаптера.

**Выход `ValidatedMatchSnapshot`:** внутренний неизменяемый объект со следующими полями:

| Поле | Тип и правило |
|---|---|
| `schema_version` | Строка `1`. |
| `match_id` | Нормализованная строка uint64, равна входному ID. |
| `fetched_at` | UTC date-time с `Z`, время завершения чтения успешного ответа. |
| `source` | Строка `deadlock-api.com`. |
| `raw_json` | Разобранный исходный JSON-объект без изменения значений; ограничен правилами адаптера. Сохраняется только при успехе всего Job. |
| `duration_s` | Конечное положительное число из `match_info.duration_s`. |
| `players` | 1–64 записи: неотрицательный целый `player_slot`, десятичная строка `account_id`, неотрицательный целый `hero_id`, команда 0 или 1. Slot уникален. |

Внешний `match_info.match_id` принимается как целое JSON-число, разобранное без потери точности, либо каноническая десятичная строка. Дробь и экспонента для ID не принимаются. Преобразование через IEEE-754 float запрещено. Account/item ID также сохраняются точно как десятичные строки; account ID 0 допустим, поскольку идентичность участника внутри матча задаёт slot.

Повреждённый JSON, дублирующиеся ключи, NaN/Infinity, отсутствие `match_info`, неверные обязательные типы, пустой/слишком большой список игроков, повтор slot или несовпадение match ID дают `SOURCE_DATA_INVALID`. Новые неизвестные поля источника игнорируются при нормализации и остаются в исходном снимке; переименование обязательного поля не угадывается.

Отсутствие или повреждение покупок, смертей, целей, рядов, координат и подписей не приводит к отказу этого Tool. Их независимо проверяет следующий шаг.

<a id="source-errors"></a>
### Ошибки источника и результат Job

У всех ошибок форма Error. Для проблем источника `details.location=source`; `field` — `status`, `body` или JSON Pointer повреждённого поля. Тело внешнего ответа пользователю не копируется.

| Исход адаптера / проверки | Код Tool | Автоматический повтор и видимый исход |
|---|---|---|
| HTTP 404 | `MATCH_DATA_UNAVAILABLE` | Нет; `failed`. Сообщение: данные недоступны в источнике, без утверждения о несуществовании матча. |
| Ошибка сети, DNS, TLS, обрыв или timeout 30 с | `SOURCE_UNAVAILABLE` | Да, при бюджете; `retry_wait`, после третьей попытки `failed` с тем же кодом. TLS-проверка не отключается. |
| HTTP 429 | `SOURCE_RATE_LIMITED` | Да, с `Retry-After`; при исчерпанном бюджете или ожидании >120 с — `failed`. |
| HTTP 500/502/503 | `SOURCE_UNAVAILABLE` | Да, с теми же правилами; ожидание >120 с завершает `SOURCE_RATE_LIMITED`. |
| HTTP 504 | `SOURCE_QUERY_TIMEOUT` | Нет; `failed`, одинаковый запрос автоматически не повторяется. |
| HTTP 401/403 | `SOURCE_ACCESS_DENIED` | Нет; `failed`, без обхода ограничений источника. |
| Прочие HTTP 4xx | `SOURCE_REQUEST_REJECTED` | Нет; `failed`, не выдать за неверный ввод пользователя после принятия Job. |
| 3xx, прочие 2xx кроме 200, прочие 5xx, неверный Content-Type | `SOURCE_PROTOCOL_ERROR` | Нет; `failed`, редиректы не выполняются. |
| 200 с повреждённым JSON, неверным минимальным набором или ID | `SOURCE_DATA_INVALID` | Нет; `failed`; `details` указывает проблемное поле, если его можно выделить. |
| Ответ больше 32 MiB после распаковки | `SOURCE_RESPONSE_TOO_LARGE` | Нет; поток чтения прерывается, `failed`. |

`retryable=true` только для `SOURCE_UNAVAILABLE` и `SOURCE_RATE_LIMITED`; для остальных строк — `false`. `retry_at` содержит нормализованное время из корректного `Retry-After`, иначе `null`. Базовые задержки 5/30 секунд и максимум трёх попыток применяются по [автомату Job](job-lifecycle.md#retry). Сетевой timeout на 30-й секунде — временный отказ; повреждённый JSON, пришедший раньше, не нужно ждать до таймаута.

<a id="build"></a>
## Tool 2 — build_match_report@1

**Назначение:** построить нормализованный отчёт и сохранить различие между отсутствием данных и настоящим нулём.

**Вход `BuildReportInput`:** объект `snapshot` типа `ValidatedMatchSnapshot` и `catalog` — неизменяемый локальный снимок справочника либо `null`. Справочник содержит версию, UTC-время загрузки и отображения строковых ID героев/предметов в подписи. Неполный справочник допустим. Контекст содержит ID того же Job. Tool не выполняет сеть и не читает произвольные файлы.

**Выход:** `MatchReport`, полностью описанный в `components.schemas.MatchReport` [OpenAPI](api/openapi.yaml). Он содержит сводку, участников, шесть разделов, предупреждения и источник. `job_id` равен контексту; `match_id`, `duration_s`, `source.fetched_at` — проверенному снимку.

### Правила преобразования

| Раздел | Источник и правила |
|---|---|
| Сводка и игроки | `match_info` и `players`; ID/длительность/slot/team обязательны. Неподтверждённый победитель, K/D/A или net worth — `null` и предупреждение, не ноль. Подписи из кеша или `null`, исходные ID сохраняются. |
| `items` | `players[].items`; подтверждённые покупки и продажи сортируются по `time_s`, затем slot, item ID, action. `sold_time_s=0` — маркер отсутствующей продажи, событие продажи не создаётся. Неизвестные флаги обновления предмета не выдаются за покупку без проверенного соответствия. |
| `deaths` | `players[].death_details`; `victim_slot` — slot владельца блока, время из `game_time_s`; неизвестный/отсутствующий убийца — `killer_slot=null`, без выдуманного игрока. |
| `objectives` | `match_info.objectives`; только подтверждённое время разрушения и ID цели. Команда обозначает принадлежность цели по источнику, не автоматически команду убийцы. |
| `economy` | Подтверждённые срезы `net_worth` с реальным временем и slot; текущее значение, не сумма срезов. Нет времени/значения — блок непригоден. |
| `damage` | Только проверенные накопительные `hero_damage_total` по времени/slot. `damage_matrix` без подтверждённого соответствия типов и времени даёт `unsupported`; не преобразуется в журнал попаданий. |
| `trajectories` | `match_paths`: проверенные версия, `interval_s>0`, разрешения, границы и равные длины X/Y для каждого slot. Мировые координаты и времена восстанавливаются только по подтверждённой схеме версии; до такой проверки блок `unsupported`. Пропуски не интерполируются. |

Для каждой поддерживаемой версии координат декодирование проверяется на контрольной metadata-фикстуре: известные точки должны совпасть с ожидаемыми мировыми X/Y и ориентацией карты. Пока такое соответствие не проверено, блок получает `unsupported`. Корректный пустой массив допускается.

Времена — конечные числа в `[0, duration_s]`; slot каждой записи должен существовать в сводке. Массив событий сортируется детерминированно, ряды — по slot и времени. Повтор временной отметки с противоречащими значениями делает соответствующий блок `invalid`; полностью одинаковые записи можно убрать как дубликаты. В trajectories разность соседних времён больше `interval_s` означает разрыв сегмента. Путь игрока выбирает ближайший **предыдущий** доступный отсчёт только внутри того же непрерывного сегмента; через пропуск положение неизвестно.

Дополнительный блок проверяется целиком: одна повреждённая запись делает этот блок `invalid`, остальные блоки остаются. Если обязательный для сборки секции подблок хотя бы одного игрока отсутствует, секция `unavailable`; неполный список не выдаётся за полный. У известных корректных пустых массивов — `available` с `data=[]`. Отсутствие целого блока — `unavailable`, неизвестная версия/семантика — `unsupported`; у всех трёх `data=null`, непустая причина и предупреждение с JSON Pointer секции. Это сознательно грубая гранулярность v1; внутри секции частичное покрытие не обещается.

<a id="bounds"></a>
### Объём результата

В секциях items/deaths/objectives/economy/damage не более 20 000 записей, trajectories — до 64 игроков и 20 000 точек на игрока. Превышение делает **эту секцию** `invalid`, `data=null`, с предупреждением `OPTIONAL_DATA_TOO_LARGE`; молчаливого обрезания нет.

Если суммарный JSON отчёта превышает 16 MiB UTF-8, исключаются целые дополнительные секции в фиксированном порядке: trajectories, damage, economy, items, deaths, objectives. Каждая исключённая секция получает `invalid`, `data=null` и предупреждение о размере; после каждого шага размер проверяется повторно. Если и обязательная сводка с предупреждениями не помещается — `RESULT_TOO_LARGE`, `failed`. Предупреждения группируются по полю/причине, не выдаются по одному на каждый отсчёт; максимум 200. Сведения о числе сгруппированных случаев можно включить в `message`.

### Ошибки второго Tool

| Код | Причина | Повтор и результат |
|---|---|---|
| `TOOL_INPUT_INVALID` | Dispatcher передал невалидный снимок/контекст | `retryable=false`, `failed`. |
| `PROCESSING_TIMEOUT` | Подготовка заняла больше 20 с либо истёк общий deadline 60 с | `retryable=false`, `failed`, без публикации частичного отчёта. |
| `RESULT_TOO_LARGE` | Обязательная часть результата не укладывается в 16 MiB | `retryable=false`, `failed`. |
| `TOOL_OUTPUT_INVALID` | Результат не проходит схему/межполевую проверку | `retryable=false`, `failed`. |
| `INTERNAL_TOOL_ERROR` | Необработанная ошибка реализации | `retryable=false`, `failed`, без внутренних подробностей в сообщении. |

Отсутствующие подписи, покупки, карта или дополнительные ряды не являются этими ошибками: возвращается успешный отчёт с предупреждениями. Оба Tool возвращают `retry_at=null` для локальных неповторяемых ошибок.

<a id="versions"></a>
## Повторяемость и версии

Job сохраняет версии обоих Tool при создании. Registry должен удерживать эти версии до завершения принятых Job. Если после релиза версия отсутствует, Job захватывается и завершается `TOOL_VERSION_UNAVAILABLE` (`retryable=false`), не выполняется молча другой реализацией. При одной версии и одинаковом снимке/справочнике второй Tool возвращает одинаковые данные, кроме полей контекста, переданных вызывающим.

Повтор первого Tool может получить более свежие metadata. Смешивать данные разных попыток нельзя: второй Tool строит отчёт из одного снимка. После публикации результат неизменен; новый сбор требует нового Job. Потерянная попытка не публикует ничего после отзыва владения, даже если оба Tool уже вернули успех.

## Критерии приёмки

| Вход / воздействие | Ожидаемый результат |
|---|---|
| Валидный ID и metadata с обязательными полями | Первый Tool возвращает снимок того же матча; второй — валидный MatchReport. |
| HTTP 503, затем корректный 200 | Два захвата, `running → retry_wait → queued → running → succeeded`; два внешних GET всего. |
| 200 с чужим match ID | `SOURCE_DATA_INVALID`, второй Tool не вызывается. |
| Обязательные данные верны, X/Y разной длины | Успех, trajectories `invalid`, другие секции сохранены. |
| Нет кеша названий | Успех, исходные ID и `LABEL_UNAVAILABLE`. |
| Тот же снимок и кеш дважды | Одинаковое содержимое отчёта при одинаковом контексте; Tool не создаёт Job и не публикует результат. |
| Устаревшая попытка вернула отчёт после Recovery | Store отвергает `STALE_ATTEMPT`; доступен только результат действующей попытки. |
