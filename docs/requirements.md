# Требования к FairfaxStat

## Цель и границы

Пользователь должен получить понятный отчёт по конкретному завершённому матчу Deadlock, не разбирая исходный JSON самостоятельно. Обработка выполняется асинхронно: запрос на создание не удерживает HTTP-соединение до окончания загрузки и анализа.

Основной источник — `api.deadlock-api.com`. Прямую интеграцию с Valve не реализуем. Границы первой версии описаны в [README](../README.md).

В документе пять сценариев: С1–С3 — основной путь, С4–С5 — ошибочные сценарии. Для каждого предусмотрен отдельный backlog issue.

## Термины и общие правила

- **match ID** — положительный целочисленный идентификатор матча. Ввод принимается как десятичная запись без знака, дробной части и экспоненты; пробелы по краям удаляются. Значение должно помещаться в беззнаковое 64-битное число. Ведущие нули нормализуются.
- **Job** — сохранённая задача получения и обработки данных одного матча. У неё есть `job_id`, нормализованный `match_id`, состояние, время создания/изменения, число начатых попыток и, при завершении, результат либо код ошибки.
- **Ключ отправки** — идентификатор одной отправки формы. Повтор той же отправки с тем же ключом не создаёт новый Job. Новая осознанная отправка получает новый ключ и может создать новый Job для того же матча.
- **Минимальные данные отчёта** — совпадающий с запросом `match_id`, корректная положительная длительность и непустой список участников с идентификаторами, героями и командами. Данные другой игры не могут быть выданы за запрошенную.
- **Дополнительные блоки** — покупки, смерти, цели, временная статистика и траектории. Они проверяются отдельно. Отсутствие или непригодность одного такого блока не уничтожает корректные остальные разделы.
- **Нет данных** отличается от значения `0`. Пустая коллекция, разрешённая контрактом, отображается как «событий не зафиксировано в ответе»; отсутствующий или непригодный блок — как «данные недоступны» с пояснением.

Времена игровых событий показываются относительно начала матча, например `15:25`. Время получения ответа хранится в UTC и отображается с указанием часового пояса. Графики и карта не дорисовывают отсутствующие отсчёты и не обещают покадровую точность.

## С1. Создать анализ матча

**Цель:** поставить конкретный матч на обработку и получить идентификатор задачи.

**Предусловие:** сервис принимает запросы; пользователь знает match ID. Наличие данных у внешнего источника проверяется уже при выполнении Job.

**Основной поток:**

1. Пользователь открывает форму и вводит match ID.
2. Интерфейс формирует ключ отправки и отправляет данные на backend.
3. Backend проверяет и нормализует ID, проверяет ключ отправки.
4. Backend сохраняет новый Job в состоянии `queued` и подтверждает постановку HTTP 202 с `job_id` и текущим состоянием.
5. Интерфейс открывает страницу состояния Job.

**Критерии приёмки:**

- **Дано:** корректный ID и новый ключ отправки. **Когда:** пользователь отправляет форму. **Тогда:** создан ровно один Job; ответ содержит его ID, нормализованный match ID и состояние; завершение анализа не является условием получения ответа.
- **Дано:** для пары «ключ отправки + match ID» уже существует Job. **Когда:** тот же запрос повторяется, в том числе после потери первого HTTP-ответа. **Тогда:** возвращается тот же `job_id`, новый Job не создаётся.
- **Дано:** два одновременных одинаковых запроса с одним ключом. **Когда:** backend обрабатывает их. **Тогда:** в постоянном хранилище остаётся один Job; оба успешных ответа ссылаются на него.
- **Дано:** ключ уже использован для другого match ID. **Когда:** приходит запрос с этим ключом и новым ID. **Тогда:** backend возвращает HTTP 409 и не меняет существующий Job.
- **Дано:** сохранить Job не удалось. **Когда:** backend обрабатывает запрос. **Тогда:** он не возвращает успешную постановку; интерфейс сообщает, что задача не создана, и сохраняет ключ для безопасного повтора.

## С2. Отследить выполнение Job

**Цель:** понять, обрабатывается ли матч, и восстановить просмотр после обновления страницы.

**Предусловие:** Job создан; пользователю известен его `job_id`.

**Основной поток:**

1. Пользователь открывает страницу Job.
2. Интерфейс запрашивает текущее состояние и периодически обновляет его до завершения.
3. Сервис показывает очередь, выполнение либо ожидание повторной попытки. Процент готовности без достоверного основания не показывается.
4. При `succeeded` появляется доступ к отчёту; при `failed` — понятная причина ошибки.
5. После обновления страницы интерфейс читает тот же Job из постоянного хранилища.

**Критерии приёмки:**

- **Дано:** существующий Job. **Когда:** пользователь запрашивает его состояние. **Тогда:** он получает его `job_id`, `match_id`, текущее состояние и время последнего изменения.
- **Дано:** Job находится в `retry_wait`. **Когда:** открыта страница состояния. **Тогда:** отображаются ожидание, число начатых попыток и время следующей попытки, если оно определено.
- **Дано:** задача выполняется или завершена. **Когда:** пользователь обновляет страницу. **Тогда:** используется прежний `job_id`; новая задача не создаётся.
- **Дано:** неизвестный `job_id`. **Когда:** пользователь открывает страницу. **Тогда:** backend возвращает HTTP 404, интерфейс показывает «Задача не найдена».
- **Дано:** backend временно не отвечает на запрос состояния. **Когда:** интерфейс не получает ответ. **Тогда:** он сообщает о проблеме связи, но не объявляет сам Job неуспешным.
- **Дано:** Job ещё не завершён. **Когда:** запрошен его отчёт. **Тогда:** сервис возвращает состояние «результат пока не готов» и не публикует промежуточный файл как готовый отчёт.

## С3. Просмотреть отчёт по матчу

**Цель:** изучить итог игры и её развитие по доступным данным.

**Предусловие:** Job завершён в состоянии `succeeded`.

**Основной поток:**

1. Пользователь открывает отчёт.
2. Сервис показывает match ID, длительность, результат, команды и участников; неподтверждённые значения отмечаются как отсутствующие.
3. Пользователь выбирает игрока и просматривает итоговую статистику, покупки/продажи и доступные события.
4. Пользователь изучает временные срезы ресурсов и урона, выбирает игрока и момент на карте перемещений.
5. Пользователь видит источник, время получения данных и предупреждения об ограничениях отчёта.

**Критерии приёмки:**

- **Дано:** фиксированный корректный JSON матча. **Когда:** сформирован отчёт. **Тогда:** ID, длительность, участники и присутствующие итоговые значения совпадают с этим JSON; неполученные значения не заменены нулями.
- **Дано:** есть покупки и продажи. **Когда:** пользователь открывает раздел предметов. **Тогда:** отображаются предметы и подтверждённые времена событий в хронологическом порядке; значение-маркер отсутствующей продажи не превращается в продажу на нулевой секунде.
- **Дано:** доступны события смертей или целей. **Когда:** открыт таймлайн. **Тогда:** время и участники событий соответствуют источнику; неподтверждённые дополнительные участники не добавляются.
- **Дано:** есть временные статистические срезы. **Когда:** построен график. **Тогда:** используются реальные временные отметки, единицы и тип показателя указаны; накопительные значения не суммируются между срезами как независимые события.
- **Дано:** есть корректные `match_paths`, границы координат, разрешение и `interval_s`. **Когда:** пользователь выбирает игрока и время. **Тогда:** карта использует соответствующий доступный отсчёт; соответствие декодированных координат карте проверено на контрольной фикстуре. Пропуски не соединяются в достоверный путь.
- **Дано:** нет траекторий либо их массивы/координатные параметры некорректны. **Когда:** отчёт открыт. **Тогда:** карта недоступна с пояснением, остальные корректные разделы работают; Job имеет `succeeded` с предупреждением.
- **Дано:** справочник не содержит имени героя или предмета либо временно недоступен. **Когда:** отображается запись. **Тогда:** показан исходный ID; весь отчёт не завершается ошибкой.
- **Дано:** в ответе есть `damage_matrix`, но интерпретация типа или выравнивания ряда не проверена. **Когда:** строится отчёт. **Тогда:** эти данные не выдаются за журнал попаданий и не используются в неподтверждённых расчётах.

## С4. Обработать неверный ID или отсутствие metadata

**Цель:** объяснить, почему анализ нельзя выполнить, без ложного сообщения о несуществующем матче.

**Основной ошибочный поток:**

1. Пользователь вводит пустое значение, ноль, отрицательное число, текст, дробь или значение вне допустимого диапазона.
2. Сервис отклоняет ввод; Job и запрос к Deadlock API не создаются.
3. Пользователь исправляет значение и создаёт Job по С1.
4. Если источник не предоставляет metadata для корректного ID, обработчик завершает Job с понятным кодом ошибки.
5. Пользователь видит, что данные сейчас недоступны в источнике; сервис не утверждает, что матча никогда не было.

**Критерии приёмки:**

- **Дано:** некорректный match ID. **Когда:** форма отправлена, в том числе напрямую в backend. **Тогда:** получен HTTP 400, ошибка привязана к полю, Job не создан, внешний API не вызван.
- **Дано:** корректный match ID. **Когда:** источник отвечает HTTP 404 на запрос metadata. **Тогда:** Job переходит `running → failed` с кодом `MATCH_DATA_UNAVAILABLE`; автоматического повтора этого ответа нет.
- **Дано:** источник вернул HTTP 200, но минимальные данные отчёта отсутствуют, повреждены или относятся к другому match ID. **Когда:** ответ проверен. **Тогда:** Job получает `failed` с кодом `SOURCE_DATA_INVALID`; чужие или непроверенные данные не публикуются.
- **Дано:** Job завершён с одной из этих ошибок. **Когда:** пользователь открывает его повторно. **Тогда:** причина сохранена; интерфейс не запускает новый Job автоматически.

## С5. Пережить временный сбой внешнего API

**Цель:** выполнить анализ после кратковременного сбоя либо завершить его предсказуемой ошибкой, не оставляя Job навсегда в работе.

**Основной ошибочный поток:**

1. Обработчик начинает загрузку metadata.
2. Источник возвращает HTTP 429/500/502/503 либо запрос завершается сетевой ошибкой или таймаутом.
3. Обработчик сохраняет причину, следующую попытку и переводит Job в `retry_wait`.
4. После допустимой задержки Job снова попадает в очередь и получает новую попытку.
5. При успешной загрузке формируется отчёт; после исчерпания бюджета Job завершается ошибкой.

**Начальные настройки для проверяемого поведения:** не больше 3 начатых попыток обработки одного Job; таймаут одного запроса metadata — 30 секунд; задержки без `Retry-After` — 5 и 30 секунд. Корректный `Retry-After` учитывается как минимальное время ожидания, в том числе в формате HTTP-date. Если он требует ждать больше 120 секунд, Job завершается с `SOURCE_RATE_LIMITED` и доступным временем возможного повтора; более ранний автоматический запрос не отправляется. Настройки централизованы, их изменение требует обновить проверки.

**Критерии приёмки:**

- **Дано:** последовательность ответов 503, затем корректный 200. **Когда:** обработчик выполняет Job. **Тогда:** видны переходы через `retry_wait`, выполнено две попытки, итоговое состояние — `succeeded`.
- **Дано:** HTTP 429 с допустимым `Retry-After`. **Когда:** назначается повтор. **Тогда:** запрос не отправляется раньше указанного срока; время ожидания доступно пользователю.
- **Дано:** все три попытки закончились временными сбоями. **Когда:** завершилась последняя. **Тогда:** Job получает `failed` с `SOURCE_UNAVAILABLE` либо `SOURCE_RATE_LIMITED`; четвёртая попытка не запускается.
- **Дано:** HTTP 504. **Когда:** обработчик получает ответ. **Тогда:** одинаковый запрос автоматически не повторяется; Job получает `failed` с `SOURCE_QUERY_TIMEOUT`.
- **Дано:** HTTP 401/403. **Когда:** обработчик получает ответ. **Тогда:** Job получает `failed` с `SOURCE_ACCESS_DENIED`; обход ограничений или смена аккаунта не выполняются.
- **Дано:** обработчик остановился во время `running`. **Когда:** истёк срок владения задачей и работает механизм восстановления. **Тогда:** Job переводится на ограниченный повтор либо в `failed` при исчерпанном бюджете; он не остаётся бесконечно в `running`.
- **Дано:** результат записан, но обработчик остановился до фиксации успеха. **Когда:** Job восстанавливается. **Тогда:** пользователю доступен максимум один опубликованный результат; `succeeded` не появляется без читаемого сохранённого отчёта.

## Жизненный цикл Job

**Состояния:**

- `queued` — Job сохранён и ожидает свободного обработчика.
- `running` — один обработчик владеет Job и получает/проверяет/обрабатывает данные.
- `retry_wait` — ожидается время повторной попытки после временной ошибки или восстановления.
- `succeeded` — готовый отчёт сохранён и доступен; возможны предупреждения о дополнительных данных.
- `failed` — обработка завершена без отчёта; сохранены код ошибки и понятное описание.

**Разрешённые переходы:**

1. Создание → `queued`: только после успешного сохранения Job.
2. `queued → running`: обработчик атомарно получает право выполнения и увеличивает число попыток.
3. `running → succeeded`: минимальные данные проверены, отчёт полностью сохранён и опубликован.
4. `running → retry_wait`: произошёл повторяемый сбой, бюджет попыток не исчерпан и ожидание допустимо.
5. `retry_wait → queued`: наступило время следующей попытки.
6. `running → failed`: неповторяемая ошибка, исчерпан бюджет или недопустимо долгое ожидание.
7. Просроченный `running → retry_wait`: обработчик потерян, восстановление допускает ещё попытку.
8. Просроченный `running → failed`: обработчик потерян, бюджет исчерпан.

**Инварианты:**

- `succeeded` и `failed` — терминальные состояния. Повтор по инициативе пользователя создаёт новый Job, а не меняет завершённый.
- Job не может одновременно исполняться двумя действующими владельцами. Результат старого владельца после потери права исполнения не перезаписывает состояние нового.
- Повторная доставка задания или одинакового запроса не создаёт дополнительные Job/опубликованные результаты.
- Повтор использует тот же `job_id`; число попыток никогда не сбрасывается при перезапуске процесса.
- Ошибка дополнительного блока данных даёт предупреждение в успешном отчёте. Ошибка минимальных данных даёт `failed`.
- Неуспешная проверка пользовательского ввода происходит до создания Job и в этот автомат не входит.
- Отмена, удаление и приостановка Job не входят в первую версию.

## Что предложил ИИ

Промпт, использованный при подготовке этого раздела:

> Мы проектируем сервис анализа конкретного матча Deadlock. Пользователь вводит match ID, backend создаёт асинхронный Job, обработчик получает metadata через api.deadlock-api.com, сохраняет результат, пользователь смотрит отчёт. Прямое подключение к Valve, replay parser и история всех игр вне первой версии. Найди ещё три способа сломать этот основной сценарий, помимо неверного ID, отсутствующего матча и обычной ошибки внешнего API. Для каждого опиши последовательность событий, наблюдаемую проблему и проверяемое требование, которое её предотвращает. Не считай наличие полного JSON гарантией корректности всех блоков.

Ответ ИИ и решения в этой версии требований:

Одинаковая отправка возвращает прежний Job; новый анализ того же матча по инициативе пользователя остаётся допустимым. |
