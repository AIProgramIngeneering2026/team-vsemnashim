# ADR-0003: анонимный владелец и ключ отправки

Дата: 2026-11-15. Статус: принято для первой версии.

## Контекст и ограничения

К1 и К2 требуют одного Job при двойной отправке и потере ответа. К8 требует скрыть задания другого клиента. При этом аккаунты и Steam login исключены в p1. Случайный `job_id` сам по себе не задаёт владение: получивший чужую ссылку не должен автоматически получить отчёт.

## Решение

Идентичность анонимного клиента задаёт секрет: 32 случайных байта из криптографического генератора, записанные 64 строчными hex-символами. Браузер сохраняет его до первой отправки и передаёт `Authorization: Bearer <секрет>` во всех API-запросах. Любой синтаксически корректный секрет определяет отдельную область клиента; сервер не выдаёт и не регистрирует аккаунты. В БД хранится только SHA-256 секрета. Владение секретом означает доступ к его Job.

Одна отправка формы получает `Idempotency-Key` в формате строчного UUIDv4. Пара «хеш секрета, ключ» уникальна в БД. Вместе с ключом сохраняются нормализованные `operation` и `match_id`; порядок JSON-полей, пробелы и ведущие нули ID не меняют идентичность запроса. Не сравниваем сырые тела или один только хеш без проверки нормализованных значений.

Новый ключ и валидный запрос создают Job и привязку в одной транзакции, ответ `202`. Эквивалентный повтор возвращает `200`, тот же ID и актуальное состояние. Другие параметры под тем же ключом дают `409 IDEMPOTENCY_CONFLICT`. Терминальный Job тоже возвращается без повторного запуска. Новый осознанный анализ использует новый ключ.

Ключи хранятся столько же, сколько Job; в v1 ни те ни другие автоматически не удаляются. Повтор проверяется до лимита очереди. Нельзя вернуть успешный ответ, если результат транзакции неизвестен. После таймаута клиент повторяет запрос с тем же секретом и ключом. Правила в [HTTP-контракте](../api/README.md#idempotency).

## Рассмотренные альтернативы

| Вариант | Почему не выбрали |
|---|---|
| Полноценные аккаунты / Steam OAuth | Расширяют согласованные границы проекта и требуют регистрации/входа. |
| Любой владелец ссылки на Job видит результат | Утечка ссылки становится утечкой чужого задания; К8 закрывается слабее. |
| Дедупликация только по match ID | Запрещает осознанный повторный анализ и смешивает запросы разных клиентов. |
| Ключ только в памяти или с коротким TTL | После рестарта/истечения TTL повтор потерянного ответа может создать второй Job. |

## Цена решения

Удаление секрета из браузера лишает доступа к прежним Job; восстановления аккаунта нет. Украденный секрет даёт доступ к этой области; нужны HTTPS, отсутствие секретов в URL/логах и защита веб-интерфейса от XSS. Сервис не устанавливает личность человека. Один человек может создавать несколько областей: глобальный лимит очереди ограничивает загрузку, но полноценная защита от злоупотреблений за пределами учебной v1.

## Условия пересмотра

Пересмотреть при запросе на общий доступ к отчётам, восстановление доступа, отзыв секретов, работу на нескольких устройствах или публичную эксплуатацию с квотами на человека. Перед введением TTL ключей определить максимальное окно безопасного повтора и миграцию старых Job.
