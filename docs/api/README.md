# Правила HTTP API

Нормативная спецификация: [openapi.yaml](openapi.yaml), OpenAPI 3.1.0. Этот файл дополняет схему проверками, которые нельзя выразить обычным типом поля: диапазон числовой строки, атомарность, порядок проверок, владение и поведение при гонках.

## Операции

Базовый путь — `/api/v1`. Интерфейс и API работают на одном origin по HTTPS; отдельный CORS-протокол не требуется. Формат ответов — `application/json`, кеширование всех API-ответов отключено через `Cache-Control: no-store`.

| Метод и путь | Успех | Ошибки |
|---|---|---|
| `POST /jobs` | `202` — новый сохранённый Job; `200` — эквивалентный повтор, прежний ID | `400`, `401`, `409`, `413`, `415`, `500`, `503` |
| `GET /jobs/{job_id}` | `200` — Job в любом состоянии, включая `failed` | `400`, `401`, `404`, `500`, `503` |
| `GET /jobs/{job_id}/result` | `200` — сохранённый `MatchReport` | `400`, `401`, `404`, `409`, `500`, `503` |

Отдельных методов списка, удаления, отмены, перезапуска и установки состояния нет. Форма создания передаёт только `operation` и `params.match_id`. Публичная операция `analyze_match` запускает цепочку двух внутренних Tool; сами Tool не вызываются по HTTP.

<a id="validation"></a>
## Ввод и порядок проверок

1. Проверить путь и допустимый метод по правилам маршрутизации ниже.
2. Для POST проверить `Content-Type: application/json` (допустим `charset=utf-8`), отсутствие сжатия (`Content-Encoding` отсутствует или `identity`) и ограничить фактически прочитанное тело 8 192 байтами. Не доверять одному `Content-Length`; превышение, в том числе при chunked, даёт `413`. Неверный тип/кодирование — `415`.
3. Проверить формат единственного заголовка Authorization. Без корректного секрета — `401`; данные Job не читаются.
4. Отклонить любые query-параметры: в v1 они не предусмотрены. Для GET тело должно отсутствовать; непустое тело — `400 VALIDATION_ERROR`, `details.field=body`.
5. Для POST проверить единственный `Idempotency-Key` и JSON. Неправильный UTF-8, синтаксис или дубли ключей — `400 INVALID_JSON`. Глубина больше 8 — `400 VALIDATION_ERROR`. Пустое тело — `400 INVALID_JSON`.
6. Проверить обязательные/лишние поля и типы. Для строковой неизвестной операции — `400 UNKNOWN_TOOL`; для отсутствующего поля или неверного типа — `400 VALIDATION_ERROR`. Неизвестная операция не создаёт Job и не запускает Tool. Две ошибки одного этапа допускается вернуть вместе, максимум 20, в порядке `location`, затем `field`.
7. Нормализовать `match_id`: исходная строка до 64 символов, только ASCII-цифры с ASCII-пробелами/табами/CR/LF по краям. Удалить эти краевые символы и ведущие нули, проверить целочисленный диапазон **1–18446744073709551615**. Пустая строка, ноль, знак, дробь, экспонента, внутренний пробел и JSON number запрещены. Использовать точную целочисленную проверку без float. В ответах ID всегда нормализованная строка.
8. Для GET проверить строчный UUIDv4 `job_id`: ошибка формата — `400`, поиск существования выполняется только после этого.
9. Перейти к хранилищу: проверить повтор ключа, затем вместимость очереди и атомарно создать Job; для GET — читать только область текущего клиента.

Лимиты HTTP-body и диапазона ID — разные проверки. Тело в 8 193 байта даёт `413` до разбора, а короткий JSON с недопустимым ID — `400` с полем `/params/match_id`. Ни в одном случае внешний API не вызывается.

<a id="identity"></a>
## Владелец Job

Клиент до первого запроса генерирует 32 случайных байта криптографическим генератором, сохраняет их как 64 строчных hex-символа и передаёт в `Authorization: Bearer <секрет>`. Сервер использует SHA-256 секрета как область клиента. Это анонимный доступ по секрету, без регистрации и проверки Steam-личности. Один секрет используется для создания и последующего чтения.

Запрос к чужому или отсутствующему Job возвращает одинаковые `404`, код `JOB_NOT_FOUND`, сообщение «Задача не найдена», поле `job_id` и причину `not_found`; различается только случайный `request_id`. Внутренняя причина и факт существования не раскрываются. Отдельной ошибки «чужой Job» нет. Результат проверяет того же владельца; знание URL и ID не даёт доступа.

Потеря секрета означает потерю доступа, выдача секрета другому человеку — передачу доступа. Секрет не попадает в URL, ответы, трассировки и логи. Обоснование — [ADR-0003](../adr/0003-request-identity.md).

<a id="idempotency"></a>
## Повтор отправки

`Idempotency-Key` — строчный UUIDv4, новый для каждой осознанной отправки. Браузер сохраняет пару «ключ, нормализуемый запрос» до отправки по сети; повтор после таймаута использует тот же ключ и секрет. Ключ без секрета не позволяет найти прежний Job.

| Условие | Результат |
|---|---|
| Новый ключ и валидный ввод | Одна транзакция сохраняет Job и ключ; `202`, `Location`, Job в `queued` с `attempts=0`. |
| Тот же клиент, ключ и нормализованные параметры | `200`, прежний ID, `Location` и актуальное состояние; выполненный Job не запускается заново. |
| Тот же ключ, иной `match_id` | `409 IDEMPOTENCY_CONFLICT`, поле `Idempotency-Key`; прежний Job не меняется. |
| Иной секрет, тот же ключ | Другая область: новый Job при соблюдении прочих условий; чужие данные не возвращаются. |
| Два запроса одновременно | Уникальное ограничение и транзакция оставляют один Job; один ответ `202`, второй `200`. Если БД временно занята и ожидание исчерпано — `503`, безопасный повтор сохраняет ключ. |
| Ответ потерян после commit | Повтор даёт `200` и сохранённый ранее Job, в том числе уже завершённый. |
| Ошибка до записи, невалидный ввод или очередь полна | Ключ не занят и Job не создан; исправленный запрос может использовать этот ключ. |

Ключи не истекают автоматически в v1. Поэтому повтор после перезапуска или долгого перерыва не создаёт дубликат. Идемпотентность не означает один Job на match ID: новый ключ допускает новый анализ. На ошибке соединения, `500` или `503` клиент не делает вывод, что Job точно отсутствует: при неопределённом commit он сохраняет ключ и повторяет.

<a id="errors"></a>
## Единые ошибки

Каждая HTTP-ошибка содержит `request_id` и объект `error` со всеми полями: `code`, `message`, `retryable`, `retry_at`, `details`. `details` — массив объектов `location`, `field`, `reason`; может быть пустым, если нет конкретного неверного поля. Тот же объект Error сохраняется в `Job.error` и `Job.last_error`. Имена и типы определены в `components.schemas.Error`.

Пример ошибки в параметрах запроса:

```json
{
  "request_id": "15c0a9f3-92c6-46cb-86f1-b71d629c98b4",
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Некорректные параметры запроса",
    "retryable": false,
    "retry_at": null,
    "details": [
      {
        "location": "body",
        "field": "/params/match_id",
        "reason": "expected_positive_uint64_string"
      }
    ]
  }
}
```

| HTTP / `error.code` | `location`, `field` | Значение для клиента |
|---|---|---|
| `400 INVALID_JSON` | `body`, пустая строка (корень) | Тело нельзя разобрать однозначно. |
| `400 VALIDATION_ERROR` | Путь поля; например `body`, `/params/match_id`; для ключа `header`, `Idempotency-Key` | Исправить указанное поле; Job не создан. |
| `400 UNKNOWN_TOOL` | `body`, `/operation` | Допустима только `analyze_match`. |
| `401 UNAUTHORIZED` | `header`, `Authorization` | Нужен секрет правильного формата; `WWW-Authenticate: Bearer`. |
| `404 JOB_NOT_FOUND` | `path`, `job_id` | Нет доступного Job; не раскрывается, существовал ли он у другого клиента. |
| `404 ROUTE_NOT_FOUND` | `request`, `path` | Такого маршрута нет. |
| `405 METHOD_NOT_ALLOWED` | `request`, `method` | Метод не разрешён; `Allow` содержит допустимый. |
| `409 IDEMPOTENCY_CONFLICT` | `header`, `Idempotency-Key` | Ключ относится к другому запросу. |
| `409 RESULT_NOT_READY` | `job`, `state` | Job ещё обрабатывается; повторить чтение позже. |
| `409 JOB_FAILED` | `job`, `state` | Отчёта не будет; причина в `GET /jobs/{job_id}`. |
| `413 PAYLOAD_TOO_LARGE` | `body`, пустая строка | Тело больше 8 192 байт. |
| `415 UNSUPPORTED_MEDIA_TYPE` | `header`, `Content-Type` или `Content-Encoding` | Нужен JSON UTF-8 без сжатия. |
| `503 QUEUE_FULL` | `request`, `queue` | Уже 100 незавершённых Job; `Retry-After: 5`, ключ не занят. |
| `503 STORAGE_UNAVAILABLE` | `request`, `storage` | Хранилище недоступно; `Retry-After: 5`, сохранить ключ. |
| `500 INTERNAL_ERROR` | Пустой `details` | Ошибка сервиса; сохранить ключ для повтора, не раскрывать внутренности. |

Для HTTP-ошибок `retryable=true` только у `RESULT_NOT_READY`, `QUEUE_FULL`, `STORAGE_UNAVAILABLE`, `INTERNAL_ERROR`. У остальных — `false`. `retry_at=null`, кроме `QUEUE_FULL` и `STORAGE_UNAVAILABLE`, где это время ответа +5 секунд. Значение описывает повтор данного запроса, а не разрешение «воскресить» Job.

Внешние 404/429/500 не пересылаются как статус чтения Job. Они превращаются в ошибки или ожидание самого Job по [таблице источника](../tool-contract.md#source-errors). Например, после недоступных metadata `GET /jobs/{id}` отвечает `200` с `state=failed`, `error.code=MATCH_DATA_UNAVAILABLE`; запрос результата — `409 JOB_FAILED`.

<a id="routing"></a>
## Неподдерживаемые операции

Для известного пути неподдерживаемый метод даёт `405` и `Allow: POST` для `/jobs` либо `Allow: GET` для остальных двух путей. Автоматические HEAD/OPTIONS вне контракта не включаются. Несуществующие пути, включая `/jobs/{id}/cancel` и `/jobs/{id}/restart`, дают `404 ROUTE_NOT_FOUND`. Завершающий slash не нормализуется: это другой, отсутствующий путь. Маршрутизатор возвращает ErrorEnvelope, а не HTML. Эти отказы не зависят от владельца или наличия конкретного Job.

В OpenAPI эти общие правила находятся в `x-router-errors` и `components.responses`. Они не представлены фиктивными бизнес-операциями отмены или изменения состояния.

<a id="report"></a>
## Отчёт и версия

`MatchReport` имеет `schema_version=1.0`, ссылку на свой Job, нормализованный ID матча, длительность, участников, источник и время получения. Все шесть разделов присутствуют: `items`, `deaths`, `objectives`, `economy`, `damage`, `trajectories`. Каждый содержит `availability`, `reason`, `data`.

- `available`, `reason=null`, `data=[]` означает проверенный пустой блок: «событий не зафиксировано в ответе».
- `unavailable`, `invalid`, `unsupported` означают разные причины недоступности; `data=null`, `reason` заполнено, в `warnings` есть соответствующая запись.
- Неполученная итоговая статистика и подписи равны `null`, не нулю. Числовой ID сохраняется даже без подписи.
- Игровое время в секундах относительно начала, временные отметки получения — UTC. Координаты — мировые X/Y, не пиксели интерфейса. Неподтверждённый перевод в карту не выполняется.
- Времена событий лежат в `[0, duration_s]`, ссылки на player slot относятся к `players`, slot уникален. Эти межполевые проверки выполняет Tool; JSON Schema сама их не обеспечивает.
- Отчёт не меняется после публикации. Новая версия парсера применяется к новым Job, версии Tool фиксируются при создании. Версия 1.x допускает только согласованные совместимые изменения; ломающие изменения требуют нового API/схемы и пересмотра контракта.
